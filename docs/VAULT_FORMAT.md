# MyVault Container Format v1

This document is normative for the on-disk format. The reader must reject
anything that does not match.

## 1. Container

A vault is a single SQLite 3 database file. SQLite stores only:

- the plaintext header row,
- one encrypted manifest blob,
- encrypted chunk blobs.

SQLite never receives plaintext file content, plaintext names, paths or the
master password.

Recommended file name: `<name>.vault`.

## 2. SQLite schema

`PRAGMA application_id = 0x4D59564C` ("MYVL"), `PRAGMA user_version = 1`.

```sql
CREATE TABLE vault_header (
    id                 INTEGER PRIMARY KEY CHECK (id = 1),
    format_version     INTEGER NOT NULL,      -- container format, currently 1
    vault_id           BLOB    NOT NULL,      -- 16 random bytes
    kdf_algorithm      TEXT    NOT NULL,      -- "argon2id"
    kdf_salt           BLOB    NOT NULL,      -- 16 random bytes
    kdf_params         TEXT    NOT NULL,      -- JSON, see below
    key_nonce          BLOB    NOT NULL,      -- 24 random bytes
    wrapped_master_key BLOB    NOT NULL,      -- 32-byte VMK + 16-byte tag
    created_ms         INTEGER NOT NULL       -- Unix milliseconds
);

CREATE TABLE encrypted_manifest (
    id         INTEGER PRIMARY KEY CHECK (id = 1),
    nonce      BLOB NOT NULL,                 -- 24 random bytes
    ciphertext BLOB NOT NULL,                 -- AEAD ciphertext + tag
    updated_ms INTEGER NOT NULL
);

CREATE TABLE encrypted_chunks (
    chunk_id   BLOB PRIMARY KEY,              -- 16 random bytes
    nonce      BLOB NOT NULL,                 -- 24 random bytes
    ciphertext BLOB NOT NULL                  -- AEAD ciphertext + tag
);

CREATE TABLE vault_meta (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
);
```

`kdf_params` is JSON:

```json
{
  "algorithm": "argon2id",
  "params": { "m_cost_kib": 65536, "t_cost": 3, "p_cost": 1, "key_len": 32 },
  "encryption": "xchacha20poly1305"
}
```

Readers must validate the algorithm identifiers and parameter bounds
(`m_cost_kib` 8192..1048576, `t_cost` 1..10, `p_cost` 1..8, `key_len` 32).

## 3. Canonical associated data

All AEAD operations authenticate the following structure, encoded little-endian:

| Offset | Size | Field |
| --- | --- | --- |
| 0 | 8 | domain `4D 59 56 41 41 44 00 01` ("MYVAAD\0\x01") |
| 8 | 2 | container format version (`u16`) |
| 10 | 1 | context: 1 = key envelope, 2 = manifest, 3 = chunk |
| 11 | 16 | vault id |
| 27 | 16 | object id (vault id for the envelope, zeroes for the manifest, file id for chunks) |
| 43 | 8 | chunk index (`u64`, zero for non-chunk objects) |

Total 51 bytes. Length-prefixed/fixed-width fields are used so that no two
logical contexts can encode to identical bytes.

## 4. Key envelope

```
KEK      = Argon2id(password, kdf_salt, kdf_params, 32 bytes)
AAD      = canonical_aad(1, vault_id, vault_id, 0)
wrapped  = XChaCha20Poly1305(KEK, key_nonce).seal(VMK, AAD)
```

`wrapped_master_key` length is exactly 48 bytes (32-byte key + 16-byte tag).
A wrong password, a modified nonce, a modified tag or a different `vault_id`
all produce an authentication failure, which the implementation reports as a
generic invalid-password error.

`VMK` is 32 random bytes generated by the OS CSPRNG at creation time.

Subkeys:

```
file_key     = HKDF-SHA256(salt = none, ikm = VMK, info = "myvault/subkey/file/v1", 32)
manifest_key = HKDF-SHA256(salt = none, ikm = VMK, info = "myvault/subkey/manifest/v1", 32)
```

## 5. Manifest

Plaintext manifest (before encryption) is UTF-8 JSON:

```json
{
  "version": 1,
  "created_ms": 1730000000000,
  "modified_ms": 1730000000000,
  "entries": [
    {
      "id": "00000000000000000000000000000000",
      "parent": "00000000000000000000000000000000",
      "name": "Home",
      "kind": "directory",
      "created_ms": 1730000000000,
      "modified_ms": 1730000000000,
      "size": 0,
      "chunks": []
    }
  ]
}
```

- The root entry always has id `00000000000000000000000000000000` and is its
  own parent.
- `kind` is `"directory"` or `"file"`.
- `size` is the plaintext length in bytes and equals the sum of `chunks[].len`.
- `chunks` is an ordered array of `{ "id": <16 random bytes, hex>, "len": <u32> }`.
- Directories have `size == 0` and an empty `chunks` array.
- Sibling names are unique, compared case-insensitively (Windows semantics).

Encryption:

```
AAD         = canonical_aad(2, vault_id, 0^16, 0)
ciphertext  = XChaCha20Poly1305(manifest_key, nonce).seal(JSON, AAD)
```

Validation performed after every decryption:

1. `version == 1`.
2. All ids unique; chunk ids unique and non-zero.
3. Every non-root entry has an existing directory parent; no cycles.
4. `size == sum(chunk.len)`; no duplicate chunk references.
5. Sibling names unique (case-insensitive); names valid.

## 6. Chunks

Files are split into 1 MiB plaintext chunks (configurable at build time; 4 KiB
minimum, 8 MiB maximum). Each chunk is encrypted independently:

```
AAD         = canonical_aad(3, vault_id, file_id, chunk_index)
chunk_id    = 16 random bytes
ciphertext  = XChaCha20Poly1305(file_key, nonce).seal(plaintext_chunk, AAD)
```

The manifest records plaintext chunk length and order. Decryption is streaming:
only one chunk is held in memory at a time.

Empty files have `size == 0` and no chunk records.

## 7. Write protocol

Import:

1. Validate all sources and build an immutable plan (no writes yet).
2. `BEGIN`; for each file, encrypt each chunk and `INSERT` into
   `encrypted_chunks` with a fresh random id.
3. Add the new entries to the in-memory manifest.
4. Encrypt the manifest and upsert `encrypted_manifest` row 1.
5. `COMMIT` - chunks and manifest become visible atomically.
6. Delete unreferenced staging rows (best effort).

Failure or cancellation before the commit rolls back every chunk; the previous
manifest remains authoritative. A process killed between steps 2 and 5 leaves
unreferenced chunks that are invisible and are swept on the next unlock.

Export:

1. Decrypt chunk by chunk to `.myvault-tmp-<random>.part` in the destination.
2. Verify each tag and the total length against the manifest.
3. `flush`, `sync_all`, then rename to the final name.

## 8. Versioning

`format_version` is bound into every AAD. A reader must refuse to open a
container whose `format_version` it does not implement, and must not modify it.
`PRAGMA user_version` tracks the SQLite schema independently.

## 9. What the format reveals while locked

- total file size,
- number of chunk records,
- approximate size of each file (rounded up to the chunk size),
- write activity over time.

It does not reveal names, structure, extensions, timestamps, contents, or the
master password.
